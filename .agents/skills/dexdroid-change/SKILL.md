---
name: dexdroid-change
description: Implement or maintain DexDroid using its spec-first workflow, requirement coverage, shared phone/monitor design and evidence. Use for feature, bug-fix, test, tooling, documentation and release changes in this repository.
---

Read the repository's `AGENTS.md` and relevant current `SPEC.md` contract.
Read docs/architecture/README.md and the owning feature architecture before
implementation. Record impact for every task; use the sibling architecture-review
skill and a fresh expert for possible architectural or uncertain impact. Record
findings/decision and revisit material departures; this is separate from UI and
the two final approvals.

Use `docs/CODING_PRACTICE.md` for targeted iteration, complete candidate checks,
source-bound evidence reuse, timings/rerun reasons and a freeze before final reviews.
Reconcile reusable workflow changes with agent-dev-template; keep Android details here.
Work on a feature/chore branch. `main` requires a PR and an up-to-date successful
`host` check including the two-agent approval gate. Never push directly to `main`
or bypass its protection; content changes from updating the branch need new reviews.
Read `docs/WORKFLOW.md` for the complete flow, `docs/ARCHITECTURE.md` for ownership,
`docs/DESIGN.md` for UI rules and `docs/ONBOARDING.md` for developer entry points.
For user-facing interaction changes, invoke the sibling `dexdroid-ui-review`
skill at `.agents/skills/dexdroid-ui-review/SKILL.md`. Create the UI expert, present
its concrete proposal, and resolve material user decisions before dependent UI
implementation. Exact authorized/delegated corrections need no repeated approval.
If a consequential requirement remains unclear after expert review, ask the user
and wait for the dependent decision while continuing independent work. Record the
expert, proposal, authorizing instruction/answer and acceptance consequences in the
existing change record. Re-review material departures. Non-UI work skips this gate.

Update the spec before code; map observable acceptance criteria to stable IDs
and scenario gaps in `docs/requirements.json`. Implement using the shared style
and service state. Then add/update behavior-focused acceptance/E2E tests.
For EVERY test addition, edit or deletion, reconcile concrete test references in
`docs/requirements.json`, run `python tools/coverage.py update`, inspect and commit
`docs/coverage.md` and `docs/coverage-snapshot.json` with the change. Run
`python tools/coverage.py check`; preserve explicit manual/visual/performance gaps.
Follow `docs/templates/spec.md` for new feature specs. Keep setup/quick use in
the concise README and release changes in CHANGELOG. Maintain affected high-level
architecture/feature-flow Mermaid diagrams, render/inspect them and keep onboarding
accurate. Follow `docs/EVIDENCE.md`: raw versioned runs and ZIPs stay ignored or in
Actions/release storage; track only concise summaries, descriptors/locations and
reports. Preserve raw bytes; retain failures without copying whole trees into Git.
Never use force-add to commit new raw evidence. Give reviewers bundle access and
verify hashes; explicitly state local-only, pending or expired availability. Validate local links and archived hashes with
`python tools/check_documentation.py` when reorganizing documents.

Use `CONTRIBUTING.md` for host/device commands and `docs/QUALITY.md` for scenario
selection, visual review and performance evidence. Run applicable suites
sequentially on the selected device; a device gap is unverified, not a pass.
Preserve the two-screen/rotation/Fit/input/background invariants in architecture.

For UI, inspect rendered phone and monitor screenshots and record human review;
do not silently approve new pixel baselines. Performance-sensitive work needs
measured distributions, not await timeouts. Existing assertions count only for
the behaviors they actually exercise. Keep changes small and record actual
commands, artifacts, configuration, results and remaining gaps using
`docs/templates/change.md` for substantial work.

Every release must attach a verified current-run `release-evidence.zip` and
`release-evidence.json` as well as `release-report.md` and its structured JSON companion,
generated by the release workflow from that build's JVM/tooling outcomes and
current requirement coverage. Keep the versioned copy under `testresults/`, attach
both reports with checksums and link the Markdown report from release notes.
Report explicit pass-rate denominators, skipped/unrun checks and coverage gaps;
never count historical device evidence as current passes. Missing/invalid report
evidence or archive/source/report bindings block publication. See `docs/RELEASING.md` for the generation contract.

Before ANY push or release, follow `docs/REVIEWS.md`: stage the completed candidate
and create exactly two fresh independent agents with no inherited conversation
(`fork_turns: none`). Each reviews the spec, diff, tests and evidence independently.
Both must explicitly approve the same candidate digest. Resolve findings and get
two new reviews after any content changes; never infer approval from silence.
Record actual identities, scope, verdicts and conclusions in
`reviews/approvals.json`, stage it, then run `python tools/review_gate.py check`.
Only both approvals plus passing checks permit the authorized push/release.
Push the reviewed branch, open a PR, wait for required checks, then merge through
GitHub. Release tags must refer to the merged reviewed contents on `main`.
The approval record alone is excluded from the candidate digest. Other edits
invalidate both reviews. If agents are unavailable, finish local work and report
that publication is blocked by this explicit project rule.

Format through Spotless. Never regenerate the lint baseline merely to make a
check green. Preserve UTF-8 explicitly. No deployment, publication or Goal is
implied solely by invoking this skill; follow the user's authorized task scope.

Follow docs/PRIVACY.md: real app/device captures stay private local. Use synthetic
fixtures by default. Public host inputs and indexed paths must pass check_privacy;
privacy withdrawal overrides historical retention without certifying missing bytes.
Never reintroduce removed evidence from an old clone/history.

For EVERY new version candidate (including patches/prereleases/docs-only), invoke
architecture-review after completed checks/evidence and before the two fresh final
reviewers. Task-level N/A and earlier preflight are not waivers. Require explicit
approval of the frozen pre-attestation inputs and record identity/version/baseline/
snapshot/findings/gaps. Block tag creation/push, release dispatch, signing and
publication if missing or blocked. Follow docs/RELEASING.md#release-architecture-review
for attestation-only delta checks, unchanged retry identity and final digest binding.
